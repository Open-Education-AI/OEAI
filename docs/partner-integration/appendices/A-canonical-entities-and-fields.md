# Appendix A · Canonical entities & fields

This appendix shows **what OEAI maps your data into**, so you can see where your fields and
identifiers land. **You do not need to produce these exact table or column names** — OEAI's Silver
layer does the mapping. The value of seeing it is to understand *which identifiers and grains
matter most*, and to spot where your data aligns (or needs a decision).

OEAI's model is **dimensional**: a few **dimensions** (the entities — `dim_*`) and many **facts**
(the events/results — `fact_*`). Your atomic records become facts; they're joined to dimensions
via the identifiers in [Identity & keys](../guide/04-identity-and-keys.md).

> Naming conventions: dimensions `dim_X`, facts `fact_X`; OEAI surrogate keys end in `key`
> (`organisationkey`, `studentkey`, `staffkey`); natural keys from your system are `external_id`,
> `school_id`, `student_id`, `staff_id`; `unique_key` is a composite merge key.

## dim_Organisation (schools / establishments)

| Canonical field | Meaning | You provide… |
|---|---|---|
| `external_id` | The org's id **in your system** | Your school id |
| `URN` | DfE Unique Reference Number (6‑digit) | **URN (priority)** |
| `Establishment_Number` | DfE establishment number (4‑digit) | If held |
| `LA_Code` | Local Authority code (3‑digit) | If held |
| `UKPRN` | UK Provider Reference Number (8‑digit) | If held (FE/post‑16) |
| `Organisation_Name` / `_Type` / `_Status` | Name, phase/type, open/closed | If held |
| `organisationkey` | OEAI surrogate key | *generated by OEAI* |

## dim_Student (pupils)

| Canonical field | Meaning | You provide… |
|---|---|---|
| `school_id` | School the pupil belongs to | Your school id / URN |
| `student_id` | Pupil id **within the school** | Your/MIS pupil id |
| `external_id` | Pupil record id in your system | Your pupil id |
| `UPN` | Unique Pupil Number (13‑char) | **UPN (priority)** |
| `unique_key` | Composite `school_id` + `student_id` | *derived* |
| `Forename` / `Surname` | Preferred/known name | If in scope |
| `Legal_Forename` / `Legal_Surname` / `Middle_Names` | Legal name | If in scope |
| `Sex` | Biological sex (statutory reporting) | If in scope |
| `Gender` | Gender identity | If in scope |
| `Date_Of_Birth` | DOB | If in scope |
| `studentkey` / `organisationkey` | OEAI surrogate keys / FK | *generated by OEAI* |

> A non‑MIS system (e.g. a reading app) usually does **not** populate the authoritative student
> dimension — the MIS does. You provide **facts that reference pupils via UPN + your pupil id**, and
> OEAI joins them to the existing `dim_Student`. Supplying good pupil identifiers is what makes that
> join succeed.

## dim_Staff (staff)

| Canonical field | Meaning | You provide… |
|---|---|---|
| `school_id` | School the record relates to | Your school id / URN |
| `staff_id` | Staff id in your/the MIS system | Your staff id |
| `Forename` / `Surname` / `Legal_*` | Name | If in scope |
| `Title` | Honorific | If in scope |
| `Sex` / `Gender` / `Date_Of_Birth` | Demographics | If in scope |
| `Continuous_Service_Start_Date` | Continuous service start | If held (HR) |
| `Legacy_System_ID` | Id from a previous system | If held |
| `staffkey` / `organisationkey` | OEAI surrogate keys / FK | *generated by OEAI* |

> **Richer staff identifiers** — payroll number, NI number, TRN — are used for cross‑source
> identity resolution in the HR domain and may be **net‑new** to the canonical schema for your
> module (reviewed by the OEAI Technical Authority). Provide what you hold; OEAI confirms the
> mapping during requirements.

## Facts (your atomic records)

A fact table typically carries: **identity columns** (school + person), the **record's own id**,
the **event columns** (dates, codes, values), and **standard metadata** (below). Examples of
canonical facts your data may feed:

| Domain | Canonical fact | Typical grain |
|---|---|---|
| Attendance | `fact_AttendanceSession` | per pupil · per session · per date |
| Behaviour | `fact_Behaviour` | per behaviour event |
| Assessment | `fact_Assessment` | per pupil · per assessment · per result |
| Exclusions | `fact_Exclusion` | per exclusion/suspension occurrence |
| Staff absence | `fact_StaffAbsence` / `fact_StaffAbsenceDay` | per occurrence / per day |

## Standard metadata columns

OEAI stamps every standardised record with provenance metadata. You don't produce these — but the
ones marked ⟵ are **derived from identifiers you supply**, which is why they matter:

| Column | Purpose |
|---|---|
| `_source_system` | Which source the row came from (e.g. your system's name) |
| `_source_id` | The record's native id in your system ⟵ *your record id* |
| `_oeai_ingested_at` | When OEAI ingested it |
| `_canonical_key` | Standardised cross‑source key ⟵ *built from your school + record ids* |
| `unique_key` | Merge/dedup key ⟵ *built from your identifiers* |

## National standards OEAI maps toward

Where helpful, OEAI aligns canonical fields to **DfE CBDS** (Common Basic Data Set / census), the
**School Workforce Census**, **Ed‑Fi**, and **SIF‑UK**. If your fields already match any of these,
say so in your docs — it removes ambiguity from the mapping.
